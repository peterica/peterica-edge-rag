# Case · MOC·entity 약한 청크 필터

## 문제

블로그 위키를 청크로 쪼개 임베딩하면, **본문이 거의 없는데 키워드만 풍부한 청크**가 생긴다.

대표 사례: `moc/`·`entities/`·`concepts/` 경로의 파일에 있는
- "관련 포스트" 링크 목록
- "주요 태그" 나열
- 연도 그룹핑 헤딩
- 반복되는 테이블

이런 약한 청크는 임베딩 유사도가 **가짜로 높게** 나와 top-k를 오염시킨다.
본문 검색 쿼리("쿠버네티스 graceful shutdown")를 날려도 top-3에 키워드 나열 목록이 섞여 들어오는 식.

## 초기 가정

- "문서를 많이 쌓고 임베딩을 잘 돌리면 검색 품질은 따라온다"
- 약한 청크는 임베딩 거리가 자연히 멀어져 top-k에 안 들어올 것

이 가정을 유지한 상태에서 **청크 수 118개**로 인제스트했다.

## 실험/검증

### 평가 하네스

- 22개 한국어 쿼리 (DevOps·RAG·K8s·모니터링 주제)
- 각 쿼리에 정답 청크(여러 개 가능) 라벨링
- 지표: MRR(Mean Reciprocal Rank), R@3(Recall at 3)
- 스크립트: `server/scripts/embed_eval.py`

### 실패 샘플 관찰

- 쿼리: `"쿠버네티스에서 graceful shutdown이란?"`
- 필터 전 top-3: 정답 183번 글 + MOC의 "관련 포스트" 목록 2개
- MOC 청크 본문은 실제 내용이 거의 없고 키워드만 나열

### 필터 규칙 도입

`moc/`·`entities/`·`concepts/` 경로 파일에서 아래 헤딩에 해당하는 청크 제외:
- "관련 포스트", "주요 태그"
- 연도 그룹 헤딩 (예: "2024년", "2023년 작성 글")
- 순수 링크 목록만으로 구성된 섹션

구현 위치: `server/chunk.py` (헤딩 path 기반 필터)

## 결과

| 지표 | 필터 전 | 필터 후 |
|---|---|---|
| 청크 수 | 118 | 93 (-25, -21%) |
| MRR | 0.794 | **0.947** (+0.153) |
| R@3 | 0.933 | **1.000** (+0.067) |

- 모델·차원·검색 알고리즘은 **전혀 건드리지 않음**
- 데이터 정리만으로 22 쿼리 중 실패 쿼리가 0개로 수렴

## 최종 선택

**MOC·entity·concepts 경로의 약한 헤딩 청크를 인제스트 시점에 필터링한다.**

- 필터는 `chunk.py`의 경로+헤딩 매칭으로 단순 구현
- ETag에 `chunker_version`을 포함시켜, 필터 규칙이 바뀌면 폰 DB가 자동 재동기화

## 왜 이 선택이 최소 구현에 적합한가

1. **추가 인프라 0**: 새 모델·인덱스·리랭커 없음. 데이터 정리 한 번.
2. **평가 하네스가 증거**: 22 쿼리 하나로 전후 비교가 끝나 의사결정 근거가 명확.
3. **단순한 규칙**: 경로·헤딩 매칭만으로 동작 → 새 위키 구조에 이식하기 쉬움.
4. **확장 여지 유지**: 청크가 수만 개 단위로 늘어나면 정답 라벨이 있는 쿼리 평가를 다시 돌려 필터 규칙을 진화시키면 된다. 지금은 93 청크 규모에서 MRR 0.947이면 충분.
5. **청크는 덜 쌓을수록 좋을 수 있다**는 원칙의 증거가 됨 — 최소 구현이 "덜"에 편향되는 정당성.
