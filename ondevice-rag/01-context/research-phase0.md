# 3트랙 병렬 리서치 — 쓰기 전에 물어봐야 하는 것들

ㅁ 들어가며

지난 글에서 모바일 온디바이스 RAG의 설계를 공개했다.
맥미니와 갤럭시를 협력시키는 이중 구조. 주머니 속에서 블로그 지식을 꺼내는 두 번째 뇌.
그리고 거기서 한 가지 원칙을 박았다.

> "Phase 0을 가장 먼저 둔 이유는, 여기서 실패하면 전부 낭비되기 때문이다."

설계만 멋진 건 쓸모없다.
그래서 코드를 건드리기 전에, **세 가지 불확실성**부터 답해야 했다.

- Galaxy S23 Ultra에서 Gemma 4 E2B가 정말 돌아가는가
- EmbeddingGemma의 한국어 품질은 쓸 만한가
- 맥미니 8GB가 듀얼 임베딩을 감당하는가

이 편은 Phase 0의 기록이다.

---

ㅁ 왜 리서치를 먼저 하는가

ㅇ Phase 0이 실패하면 전부 낭비된다

"먼저 만들어보고 나중에 고친다"는 빠른 길처럼 보인다.
그러나 **전제가 틀리면 만든 모든 것이 쓰레기**가 된다.
이 프로젝트의 전제 — "S23에서 엣지 LLM이 돌아간다" — 가 틀리면 서버의 듀얼 임베딩, 모바일 앱, 동기화 구조가 전부 무너진다.
설계 첫 줄부터 재검토다.

설계 초기의 불확실성은 **가장 싼 비용으로 제거할 수 있을 때**이다.
코드가 쌓인 뒤에 "안 되네"라고 깨닫는 게 가장 비싸다.

ㅇ 병렬로 나누면 시간이 줄어든다

세 가지 불확실성은 서로 독립이었다.
한 개씩 직렬로 하면 시간이 누적되지만, 병렬로 돌리면 가장 긴 하나의 시간으로 끝난다.
그래서 **3트랙 분할 + 병렬 실행**으로 설계했다.
각 트랙의 목표는 하나 — `GO / NO-GO` 판정까지 가는 것.

---

ㅁ 3트랙 설계

ㅇ Track A — Gemma 4 E2B가 S23에서 돌까

목표: 모바일 LLM 구동 가능성 확인.

검증 포인트:
- LiteRT-LM이 Gemma 4 E2B를 지원하는가 (공식 `.litertlm` 파일 존재 여부)
- Snapdragon 8 Gen 2에서의 추론 속도
- 메모리 사용량과 발열
- 가장 빠른 실기 확인 수단

결과: **GO**.
Google이 `litert-community/gemma-4-E2B-it-litert-lm` 레포로 공식 모델을 공개 중이었다.
Google Play Store에는 `AI Edge Gallery`라는 앱이 있어 Gemma 4 E2B를 받아 즉시 돌릴 수 있었다.
추론 속도는 CPU 기준 **12~20 tok/s** — RAG 용도에 충분했다.

다만 한 가지 함정.
**Snapdragon 8 Gen 2의 GPU delegate에 버그**가 있어 GPU 가속은 포기하고 CPU로 폴백했다.
성능 하락은 크지 않았다.

ㅇ Track B — EmbeddingGemma의 한국어는 믿을 만한가

목표: 모바일 임베딩 모델의 언어 품질 확인.

검증 포인트:
- 모바일 배포 경로 (LiteRT 포맷, 모델 크기)
- 한국어 검색 품질
- 대안 모델 비교

결과: **GO (조건부)**.
Google이 SM8550 전용 TFLite(184MB)를 제공하고 있어 배포 경로는 매끄러웠다.
문제는 한국어 품질 — 논문과 블로그에 "100+ 언어 지원"이라고 쓰여 있을 뿐, **한국어 전용 벤치마크는 어디에도 없었다.**

대안을 정했다.
`multilingual-e5-small-ko-v2`(384차원, 한국어 파인튜닝, MTEB-ko 평균 nDCG@10 0.693).
이건 한국어 벤치마크가 여럿 공개돼 있었다.
결정: **Phase 1에서 e5로 먼저 시작하고, 실측으로 둘을 비교**한다.

ㅇ Track C — 듀얼 임베딩을 8GB가 감당할까

목표: 서버 파이프라인 실현 가능성 확인.

검증 포인트:
- `bge-m3` + `EmbeddingGemma` 두 모델을 **8GB 안에서** 돌릴 수 있는가
- 118 청크 처리 시간
- 모바일 DB 파일 크기

결과: **GO**.
8GB에서 두 모델을 **동시에** 올리는 건 빠듯했다.
하지만 Ollama가 기본적으로 한 번에 한 모델만 메모리에 올리고, 다음 요청이 들어오면 이전 모델을 내려놓는다.
즉 **순차 실행이 제약이 아니라 해법**이었다 — 동시 메모리 부담 자체가 애초에 없었다.
118청크 기준 총 20초 이내.
모바일 DB는 1~3MB 수준으로 `GET /sync` 엔드포인트로 내려보내면 충분했다.

→ 메모리가 적은 환경에서 **Ollama의 모델 스왑 모델이 곧 설계의 답**이었다.
이게 16GB 장비였다면 "동시 로드 vs 순차 실행"을 비교했겠지만, 8GB에서는 선택지 자체가 좁아 결정이 명료해졌다.

---

ㅁ 숨은 발견들

리서치는 GO/NO-GO 판정만 주는 게 아니었다.
예상하지 못한 것들이 따라왔다.

ㅇ EmbeddingGemma는 임베딩 모델이 맞다 (Gemma 4는 생성 모델)

이름이 비슷해서 헷갈리기 쉽다.
`Gemma 4 E2B`는 **텍스트를 생성**하는 LLM, `EmbeddingGemma-300M`은 **벡터를 만드는** 임베딩 전용 모델.
둘은 용도가 다르지만 같은 LiteRT 런타임 위에서 돌고, 같은 Matryoshka 차원 기법을 공유한다.
Google이 온디바이스 RAG를 하나의 스택으로 밀고 있다는 신호였다.

ㅇ all-MiniLM은 한국어에 쓰면 안 된다

가장 유명한 경량 임베딩 모델(~25MB)이지만 **영어 전용으로 학습됐다**.
HuggingFace 공식 문서에서도 비영어는 `paraphrase-multilingual-MiniLM-L12-v2`를 쓰라고 경고한다.
작다는 이유로 가볍게 집어들면 한국어 검색이 무너진다.

→ 크기가 곧 성능이 아니다. **언어 범위**를 먼저 확인한다.

ㅇ LiteRT-LM에 SM8550 전용 파일이 따로 있다

Google의 `litert-community/embeddinggemma-300m` 레포 파일 중에 `embeddinggemma-300M_seq256_mixed-precision.qualcomm.sm8550.tflite` 같은 이름이 있었다.
즉 **Qualcomm 칩별로 따로 최적화된 TFLite**를 제공한다는 뜻.
범용 파일보다 추론 속도가 현저히 빠를 수 있다.
온디바이스 AI가 "하드웨어 친화적 생태계"로 진화하고 있음을 보여준다.

---

ㅁ 짚고 넘어갈 기술 고민

설계 리뷰가 아니라 리서치를 리뷰해본다.
실험 방식 자체에 숨은 전제들이 있었다.

ㅇ "내가 바꿀 수 없는 것"을 먼저 검증한다

리서치 대상 선정에 원칙이 있다.
내가 바꿀 수 없는 것 — **외부 생태계에 의존하는 부분**을 먼저 검증한다.
LiteRT의 지원 여부, 모델 공개 상태, 칩별 최적화 파일 존재 여부.
이런 건 내가 못 만든다. 만약 없다면 전략을 바꿔야 한다.
반대로 서버 스택이나 청킹 로직처럼 **내가 통제 가능한 부분**은 Phase 0에서 뺐다 — 거기는 언제든 만들 수 있으니까.

ㅇ 리서치의 증거는 "공식 문서 + 실기" 둘 다 필요하다

문서만 보고 판단하면 "이론상 가능" 수준에 머문다.
반대로 공식 문서 없이 실기만 하면 재현성이 없다.
Track A는 `AI Edge Gallery` 앱으로 실기, Track C는 Ollama로 실기.
Track B만 문서 기반이었는데 — 그래서 `조건부 GO`로 등급이 달라졌다.

ㅇ "GO"와 "조건부 GO"는 다른 판정이다

모든 트랙이 GO라고 해서 동등한 자신감은 아니다.
Track A·C는 **실측 GO**, Track B는 **문서 GO + 실측 미완**.
이 차이는 Phase 1 진입 시 리스크 순위에 반영됐다 — "모바일 임베딩 품질은 실측 후 확정"으로 유보 상태를 남겼다.

ㅇ 병렬 리서치는 "독립성 검증"이 선행되어야 한다

세 트랙을 병렬로 돌렸지만 이는 **서로 의존이 없다는 확인**이 먼저였다.
만약 Track B가 Track A의 결과에 의존했다면 (예: E2B 런타임이 없으면 임베딩도 못 돌림) 병렬은 성립하지 않는다.
각 트랙의 GO 조건을 독립적으로 정의하는 것이 설계의 핵심이었다.

→ 리서치도 설계다. 결과물은 문서 한 장이지만, 구조가 잘못되면 결론도 잘못된다.

---

ㅁ 생각해 볼 것들

ㅇ 리서치는 어디까지가 리서치이고 어디부터가 구현인가

Phase 0은 "코드 없이 답을 낸다"고 했지만, Track A는 **실제로 앱을 설치하고 쿼리를 넣어봤고**, Track C는 **Ollama 명령을 돌려서 시간을 쟀다**.
엄밀히 말하면 이것도 미니 구현이다.
그럼 경계는 어디인가 — 내 답은 **"프로덕션 코드가 아니면 리서치"** 다.
일회성이고 버려도 되는 확인 작업은 리서치.
재사용되고 유지보수 대상이 되면 구현.

ㅇ GPU delegate 버그 같은 건 Phase 0에서 잡히지 않는다

Track A가 "GO"였지만 Snapdragon 8 Gen 2의 GPU 이슈는 **실제 앱을 설치한 뒤**에 드러났다.
리서치는 "돌아가는가"를 보지만, "최적으로 돌아가는가"는 못 본다.
후자는 Phase 2, 3의 몫이다.

→ 리서치의 커버리지에는 한계가 있다.
Phase 0은 "설계가 가능한가"를 묻는 것이지, "최고 성능이 나오는가"를 묻는 게 아니다.

ㅇ 한국어 품질을 "공식 문서"로 판단할 수 있는가

Track B가 `조건부 GO`가 된 근본 이유는 벤치마크 없음.
그런데 반대로 생각하면, 벤치마크가 있는 모델이라도 **내 도메인(블로그 위키)에서 좋은 성능**을 낼지는 별개 문제다.
MTEB-ko의 점수가 내 블로그 검색에 그대로 옮겨간다는 보장은 없다.

→ 결국 **내 데이터로 재실측**하는 단계가 필요하다.
이건 Phase 3의 일이 될 것이다.

ㅇ "병렬로 빨리"는 항상 좋은 전략인가

세 트랙을 병렬로 돌렸지만, 직렬로 했다면 Track A 결과를 본 뒤 Track B·C를 포기하거나 방향을 바꿀 수도 있었다.
병렬은 빠르지만 **중간에 배운 것을 다음 트랙에 반영할 수 없다.**
지금처럼 세 축이 명확하고 독립적일 때는 병렬이 맞지만, 불확실성이 높을 때는 **순차적 탐색**이 오히려 나을 수 있다.

→ 속도보다 "다음 단계에 반영할 여지"를 먼저 본다.

---

ㅁ 마무리

Phase 0에는 코드 한 줄 남지 않았다.
하지만 그 뒤의 모든 결정이 이 판정 위에 서 있다.
"돌아간다"고 확인한 모델을 믿고 서버를 포팅했고, "조건부"라고 남긴 임베딩을 Phase 3에서 다시 측정하기로 했다.

→ 리서치는 코드의 사전 비용이 아니라, 보험이다.
