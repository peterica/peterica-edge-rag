# 맥미니 RAG를 넘어서 — 모바일 온디바이스 AI를 시작하다

ㅁ 들어가며

이전 글에서 나는 맥미니 위에 1,000개 블로그 문서를 검색하는 RAG 시스템을 만들었다. `bge-m3`로 임베딩하고, `sqlite-vec`로 벡터 검색하고, `exaone3.5`로 답변을 생성하는 구조였다. 마지막에 이렇게 썼다.

> "1,000개 문서는 보유만으로는 창고. 검색이 붙는 순간 두 번째 뇌가 된다."

그런데 이 두 번째 뇌에는 한계가 있었다. **맥미니가 켜져 있어야만 작동한다.** 와이파이가 없으면, 서버가 내려가면, 내 지식에 접근할 수 없다. "기술 선택은 항상 '지금의 문제 크기'에 맞춰야 한다"고 했는데 — 지금의 문제는 **검색이 특정 장소에 묶여 있다는 것**이다.

그래서 질문을 바꿨다. 서버 없이, 내 손 안에서 검색과 응답이 가능할까?

---

ㅁ 왜 모바일인가

ㅇ 서버 의존에서 벗어나기

맥미니 RAG는 잘 돌아간다. 하지만 나는 DevOps 엔지니어로서 단일 장애점(SPOF)이 거슬린다. 서버가 곧 뇌라면, 서버가 죽으면 뇌도 죽는다. 모바일에 로컬 검색을 올리면 최소한 오프라인에서도 문서를 찾을 수 있다.

ㅇ 엣지 AI를 직접 경험하고 싶다

솔직히 말하면, 호기심이 가장 크다. 2025년부터 온디바이스 LLM이 실용 단계에 진입했다는 글을 수없이 읽었다. 읽는 것과 직접 돌려보는 것은 다르다. Galaxy S23 Ultra의 Snapdragon 8 Gen 2에서 실제로 LLM이 돌아가는지, 한국어 응답 품질이 쓸 만한지 — 이건 해봐야 안다.

ㅇ 학습 목적이 가장 크다

이 프로젝트는 기능 개발이 아니라 **시스템 구조를 이해하기 위한 학습 프로젝트**다. RAG를 넘어서 임베딩 파이프라인, 벡터 검색, 프롬프트 엔지니어링, 그리고 리소스 제약 하의 설계를 직접 경험하는 게 목적이다.

---

ㅁ 시스템 구조 — 맥미니 + 갤럭시의 협력

전체 구조는 이렇다.

```
[Galaxy S23 Ultra]
질문 입력
 ├─ 로컬 경로:
 │   → EmbeddingGemma-300M (쿼리 임베딩)
 │   → SQLite 로컬 검색 (top-k)
 │   → Gemma 4 E2B (답변 생성)
 │
 └─ 서버 경로 (fallback):
     → Mac Mini REST API
         ↓
     [Mac Mini]
     → bge-m3 임베딩
     → sqlite-vec 검색
     → minja 프롬프트 렌더링
     → LLM 실행
     → 응답 반환
```

쉽게 말하면, 모바일이 먼저 시도하고 안 되면 서버에 물어보는 구조다.

ㅇ 왜 이중 구조인가

한쪽만 쓰면 되지 않느냐고 할 수 있다. 하지만 모바일과 서버는 각각 다른 강점이 있다.

| 항목 | Galaxy S23 Ultra | Mac Mini |
|------|------------------|----------|
| 장점 | 오프라인, 즉시 응답, 항상 휴대 | 고품질 LLM, 큰 모델, 풍부한 컨텍스트 |
| 단점 | 작은 모델, 제한된 메모리 | 네트워크 필수, 장소 종속 |

둘을 결합하면 — 평소에는 주머니 속의 가벼운 검색, 필요하면 서버의 깊은 답변. 이게 하이브리드의 핵심이다.

---

ㅁ 핵심 기술 선택과 이유

ㅇ 모바일 LLM: Gemma 4 E2B

Google이 엣지 디바이스용으로 내놓은 모델이다. 실효 2.3B 파라미터인데, 내부 아키텍처 최적화로 더 큰 모델 수준의 표현력을 낸다. 4bit 양자화하면 약 1.5GB. S23 Ultra의 12GB RAM에서 충분히 여유가 있다.

선택 근거를 정리하면:
- 1.5GB로 12GB RAM 내 여유 확보
- 128K 토큰 컨텍스트 → RAG 컨텍스트 주입에 충분
- LiteRT 공식 지원 (Google AI Edge 생태계 통일)
- Apache 2.0 라이센스

ㅇ 모바일 임베딩: EmbeddingGemma-300M

온디바이스 임베딩 모델 후보가 여럿 있었다. `multilingual-e5-small-ko-v2`(한국어 파인튜닝), `gte-multilingual-base`, 그리고 `EmbeddingGemma-300M`.

EmbeddingGemma를 선택한 이유:
- INT4 양자화로 200MB 미만
- Matryoshka 차원 지원 (128/256/512/768) → 품질-크기 트레이드오프 조절 가능
- LiteRT 공식 지원 → Gemma 4 E2B와 동일 런타임, 통합이 간결해진다
- EdgeTPU 기준 15ms 미만 추론 (256 토큰)

ㅇ 임베딩 불일치 문제

여기서 한 가지 고민이 생긴다. 서버는 `bge-m3`(1024차원), 모바일은 `EmbeddingGemma`(768차원). 임베딩 모델이 다르면 동일 쿼리로 다른 검색 결과가 나온다.

대응 전략은 간단하다 — **임베딩 파이프라인을 2벌 운영한다.** 서버에서 ingest할 때 두 모델로 각각 임베딩 DB를 생성하고, 모바일 DB는 `GET /sync`로 내려받는 구조다. 깔끔하진 않지만, 118개 청크 규모에서는 이 정도 중복이 문제가 되지 않는다.

ㅇ 서버 스택: Next.js에서 FastAPI로

이전 blog-chat은 Next.js + AI SDK v6으로 만들었다. 이번에는 FastAPI로 바꿨다. 이유는 단순하다 — llama.cpp 기반 추론과 minja 프롬프트 엔진이 핵심인데, `llama-cpp-python` 바인딩이 있는 Python이 자연스럽다. 임베딩 파이프라인도 `sentence-transformers`, ONNX 등 Python 생태계가 훨씬 풍부하다.

---

ㅁ 개발 계획 — 3단계 순차 + 리스크 선행

```
Phase 0: 리스크 검증 (Spike)
├─ S23 Ultra에서 Gemma 4 E2B 구동 가능?
├─ EmbeddingGemma-300M 온디바이스 추론 가능?
└─ 여기서 실패하면 → 전체 아키텍처 재검토

Phase 1: Server (Mac Mini - FastAPI)
├─ 기존 RAG 파이프라인 Python 포팅
├─ 듀얼 임베딩 ingest
└─ /query, /sync API

Phase 2: Mobile (Android - Kotlin)
├─ 로컬 검색 + LLM 응답
├─ 서버 연동 (fallback)
└─ 통합 테스트
```

Phase 0을 가장 먼저 둔 이유가 있다. 이 프로젝트의 최대 불확실성은 "Galaxy S23 Ultra에서 Gemma 4 E2B가 진짜 돌아가는가?"다. 서버를 아무리 잘 만들어도, 모바일이 안 되면 듀얼 임베딩 파이프라인 전체가 낭비된다. 검증 방법은 Google의 AI Edge Gallery 앱으로 실기 테스트를 하는 것이다.

ㅁ 리소스 예산

Galaxy S23 Ultra의 12GB RAM을 어떻게 쓸 것인지 미리 계산해봤다.

```
총 RAM: 12GB
─────────────────────────────────────
OS + 기본 앱:                  ~4.0GB
─────────────────────────────────────
Gemma 4 E2B (4bit):           ~1.5GB
EmbeddingGemma-300M (INT4):   ~0.2GB
SQLite DB:                     ~0.001GB (118 청크)
앱 런타임 (Kotlin + Compose):  ~0.3GB
─────────────────────────────────────
AI 총 사용:                    ~2.0GB
여유:                          ~6.0GB ✓
```

6GB 여유. 숫자상으로는 넉넉하다. 하지만 숫자와 실제는 다르다 — 그래서 Phase 0이 필요하다.

ㅁ 짚고 넘어갈 기술 고민

설계 위에 올라간 기술 결정 중에, 한 번 더 짚고 갈 만한 포인트들이 있다. 어떤 건 축이 하나가 아니어서, 어떤 건 이유를 오해하기 쉬워서.

ㅇ 온디바이스의 존재 이유는 한 축이 아니다

왜 서버 위에 RAG가 있는데도 굳이 모바일까지 가는가. "개인 특화"만으로는 충분하지 않다. 온디바이스의 존재 이유는 최소 세 축이다.

- **오프라인 가용성** — 서버 장애·네트워크 단절과 독립
- **즉시성** — 네트워크 왕복 없이 바로 응답
- **프라이버시** — 내 데이터가 서버로 올라가지 않음

AI 시대에 프라이버시 축은 점점 더 무거워진다. 온디바이스는 서버의 대체가 아니라, **"서버로는 못 하는 것을 가능하게 하는 것"** 이다.

ㅇ 하이브리드의 두 축 — 속도와 품질

모바일과 서버를 나누는 기준을 "속도"로만 보면 절반만 맞는다. 다른 한 축은 **답변 품질**이다. 모바일 LLM은 2.3B(Gemma 4 E2B), 서버 LLM은 4~8B. 모델 크기가 다르다. 속도는 모바일이 빠르지만, 깊은 추론은 서버가 강하다. 이 구조는 "같은 일을 두 번 하는" 것이 아니라, **"다른 일을 각자 잘하는"** 구조다.

ㅇ 임베딩 불일치 — "왜 생기나"와 "어떻게 푸나"는 다른 질문이다

서버는 `bge-m3`(1024차원), 모바일은 작은 모델(384차원). **왜 다른가**는 디바이스 리소스 제약이다. 그런데 **어떻게 푸나**는 별개의 설계 결정이다. 이 프로젝트의 답은 `DB를 두 벌 만드는 것` — 같은 지식을 서로 다른 임베딩 모델로 각각 "번역"해서 `server.db`, `mobile.db`로 분리한다. 폰은 필요한 쪽만 내려받는다. 중복이지만, 규모가 작을 때는 감수할 만한 트레이드오프다.

ㅇ FastAPI의 선택 근거는 프레임워크 성능이 아니다

Python 기반이라는 점 때문에 "디바이스 성능을 더 쓴다"고 오해하기 쉽다. 그런 이유가 아니다. 서버는 맥미니에서 돌고, FastAPI 자체도 `C계열`이 아니다. 진짜 이유는 `Python의 AI 생태계` — `llama-cpp-python`, `sentence-transformers`, ONNX, minja. AI/ML 도구가 Python에 압도적으로 많다. **"언어를 갈아타면 열리는 도구 창고"** 가 이 선택의 본질이다.

ㅇ Phase 0은 "Fail Fast"를 구체화한 장치다

Phase 0의 존재 이유는 한 원칙으로 정리된다 — `Fail Fast`. 가장 불확실한 걸 제일 먼저 검증한다. 이 프로젝트에서는 "S23에서 Gemma 4 E2B가 진짜 돌아가는가"가 그것. 이게 실패하면 듀얼 임베딩 파이프라인도, 모바일 앱도 전부 무용지물이 된다. 땅이 무너지는지부터 확인하고 집을 짓는 셈이다. 설계 초기의 불확실성을 숫자가 아니라 실측으로 없애는 것이 Phase 0의 역할이다.

→ 설계는 대충 알겠는데, 말로 풀어내려 하면 어디가 얕은지 드러난다.

ㅁ 생각해 볼 것들

이 프로젝트를 시작하며 완전히 결론내리지 못한, 그러나 계속 생각하게 되는 질문들이 있다. 
지금 내 생각을 적어두고, 시간이 지난 뒤 답이 바뀌었는지 다시 본다.

ㅇ 왜 작은 모델이 개인 도메인에 더 유리할 수 있을까?

보통 "모델이 클수록 좋다"고 생각한다. 그런데 나만의 블로그 1,000개 같은 **좁은 도메인**에서는 이 가정이 흔들린다. 
거대 모델의 일반 지식은 내 문맥에서 오히려 노이즈가 될 수 있다. 
모델이 아는 게 너무 많으면 내 문서와 무관한 "일반적 정답"으로 흘러가기 쉽다. 
작은 모델 + 좋은 검색은, 큰 모델 + 나쁜 검색보다 개인 도메인에서 정확할 수 있다. → 크기보다 `문맥에 얼마나 맞는가`가 중요하다.

ㅇ 온디바이스 AI는 서버를 대체할까, 보완할까?

둘 다 답이 가능하지만, 내 답은 **"보완"** 이다. 
하드웨어가 발전해도 서버와 모바일의 상대적 격차는 유지된다. 
모바일이 5B급이면 서버는 70B급, 모바일이 70B급이 되면 서버는 300B급이 된다. 
복잡한 추론·최신 정보·깊은 답변은 서버가 유리하고, 즉각성·프라이버시·빈번한 질문은 디바이스가 유리하다. 
결국 둘이 역할을 나누는 구조로 갈 가능성이 높다.

ㅇ 임베딩 모델 불일치를 "DB 두 벌"로 풀었다. 더 나은 방법은 없을까?

지금은 같은 문서를 두 번 임베딩해서 중복 저장한다. 
118개 청크에서는 문제 없지만 10만 개가 되면 낭비다. 
대안을 생각해보면:

- (1) 공통 차원으로 맞추는 projection 레이어 학습 — 학습 리소스 필요
- (2) 서버는 큰 모델, 모바일은 작은 모델로 각각 최적화하고 불일치를 감수 — 지금 방식
- (3) Matryoshka 구조 모델 하나로 통일하되 차원만 잘라서 쓰기 — EmbeddingGemma가 이를 지원

장기적으로는 (3)이 가장 우아해 보인다.

ㅇ "내 뇌를 주머니에 넣는다"는 비유의 한계는?

뇌는 학습·연결·창발을 한다. 지금 RAG는 `검색 + 생성`만 한다. 
내가 어제 배운 것을 오늘 생각에 연결하지 못하고, 여러 글을 읽으며 만드는 새 통찰이 저장되지 않는다. 
진짜 두 번째 뇌가 되려면 자동 업데이트, 개념 간 연결망, 메타인지 같은 층위가 더 필요하다. 
지금 구조는 "뇌"라기보다 **"검색 가능한 노트"** 에 가깝다 — 그것만으로도 꽤 쓸 만하지만, 한계를 아는 건 중요하다.

ㅇ 완제품 AI 앱이 많은데 굳이 직접 만드는 이유는?

쓰는 것과 만드는 것은 이해의 깊이가 다르다. 
ChatGPT를 매일 써도 임베딩·검색·프롬프트 구조를 이해하게 되지는 않는다. 
특히 시스템 엔지니어링은 "왜 이 선택을 했는가"를 직접 마주해야 배워진다. 
이 프로젝트의 본질은 AI 앱을 만드는 것이 아니라, **AI 시스템의 구조를 이해하는 것**이다. 
결과물이 완벽하지 않아도 된다 — 조립 과정 자체가 목적이다.

→ 질문을 남겨두는 건, 언젠가 답이 바뀔 것을 믿기 때문이다.

ㅁ 마무리

서버 위의 RAG는 "두 번째 뇌"였다. 이제 그 뇌를 주머니에 넣으려 한다.

이전 글에서 "기술 선택은 항상 '지금의 문제 크기'에 맞춰야 한다"고 썼다. 지금의 문제는 — 서버에 묶인 지식을, 어디서든 꺼낼 수 있게 만드는 것이다. 작은 모델, 작은 메모리, 작은 배터리 안에서. 이 제약이 오히려 설계를 선명하게 만든다.

→ 제약은 한계가 아니라 설계의 출발점이다.
